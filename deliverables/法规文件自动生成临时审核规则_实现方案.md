# 法规文件 → 自动生成临时审核规则：实现方案

> 场景：用户不选择任何既有规则组 / 规则集，而是**直接上传一份法律法规文件**，
> 由模型解析全文、自动抽取并生成一组**临时审核规则**，再用这组规则审核目标文档。
>
> 状态：✅ 后端已完整落地并通过自检（40 项断言全绿）；✅ 前端已实施（`TaskWizard` 第三模式 + `LegalRulePanel` 组件，`tsc -b && vite build` 通过）；🟡 真实 LLM 联调见 `deliverables/法规挖掘联调简报.json`。

---

## 1. 设计目标与三条硬约束

| # | 约束 | 原因 |
|---|------|------|
| 1 | **不污染正式规则库** | 模型抽取的规则质量不稳定，直接写进 `rules_store.json` 会污染所有用户的规则集。默认「临时」，用户显式「转正」才落正式库。 |
| 2 | **审核引擎零改动** | 产出的规则 dict 与 `rules_store._normalize_rule` 同形，直接喂给 `review_engine.run_review`，复用全部分批/并发/一致性/落库/导出链路。 |
| 3 | **长文本必须分块** | 法规全文常达数十万字。单次送 LLM 必然撞 `llm_timeout(180s)` × `llm_max_retries(3)` 的 540s 硬顶（本项目已踩过 59k 字符文档的坑）。 |

---

## 2. 总体数据流

```
上传法规文件  →  解析全文  →  按「条」切分  →  按字符预算打包成块
     │                                              │
     │                                    ┌─────────┴─────────┐
     │                              并发（默认 3）逐块送 LLM 抽取规则
     │                                    └─────────┬─────────┘
     │                                              ▼
     │                              归一化 → 全局去重 → 打分排序 → 截断
     │                                              ▼
     │                              临时规则集（lrs-*）status=ready
     │                                              │
     │                        ┌─────────────────────┼─────────────────────┐
     ▼                        ▼                     ▼                     ▼
 前端预览/编辑          纯法规模式审核          叠加模式审核          转正为正式规则集
                    （只跑法规规则）      （内置规则 + 法规规则）   （rules_store）
```

## 3. 模块一：法规文件解析与切分

**复用既有能力**，不新造解析器：

- 上传走原 `POST /api/files/upload`，解析器 `doc_parser.parse`（PyMuPDF 读 PDF、python-docx 读 docx、
  扫描页自动 OCR，单文件上限 100MB），纯文本落在 `file_store` 记录的 `text` 字段。
- 新增文件角色 `role="legal"`，与 `tender/bid/attachment`（审核目标）区分开：
  - **法规文件不允许作为审核目标送审** —— `review._resolve_docs` 会拦截并返回 400。
    否则会把法规自身当成投标文件逐条核查，产出大量无意义结论。

**切分策略**（`legal_rules.split_legal_text`）—— 三级降级：

| 优先级 | 识别方式 | 适用 | 说明 |
|---|---|---|---|
| 1 | 正则 `^第[一二三四五六七八九十百千零〇0-9]+条` ≥ 3 处 | 法律、条例、办法 | 一条一义，**不切断条款** |
| 2 | 正则 `^第[一二三四五六七八九十百千]+[章节编]` ≥ 2 处 | 规章、标准、规范 | 章/节为边界 |
| 3 | 空行分段 | 通知、意见、批复 | 退化为段落窗口，并写入告警提示用户 |

**打包**（`pack_chunks`）：顺序累加小段至预算 `legal_chunk_chars`（默认 12000 字符）；
超预算的单段再硬切（保留 200 字符重叠，避免阈值/主体被切断）。
函数内置 `max(2000, budget)` 下限，防止误配过小预算导致块数爆炸。

## 4. 模块二：规则自动抽取

**复用 `llm_client.chat` + `parse_json`**（内置退避重试、并发闸、审计日志），
**刻意不用**引擎的 `_run_with_kb`——后者硬注入「招投标审核专家」人设，不适合抽取任务。

### Prompt 设计（`legal_rules.MINING_SYSTEM`）的关键约束

1. **只抽可核查条款**：义务性 / 禁止性 / 条件性，含明确主体、行为、标准、阈值、时限、形式要求。
2. **明确排除项**：立法目的、适用范围、术语定义、部门职责、施行日期、附则、目录、页眉页脚。
3. **checkpoints 必须是动作**：2~5 条「审核员逐项做什么」，禁止写「检查是否合规」这类空话。
4. **严禁编造**：`legal_basis` 必须是原文真实存在的条/款/项号；宁可少抽不可虚构。
5. **类别禁用 `consistency`**：见第 7 节的误判防护。
6. `temperature=0.0`：抽取任务要可复现。

### 输出契约

```json
{"rules": [{
  "name": "投标保证金不得超过项目估算价的2%",
  "category": "commercial",
  "severity": "critical",
  "description": "判定标准说明",
  "checkpoints": ["提取投标保证金金额", "与项目估算价比较是否超过2%"],
  "legal_basis": "第二十六条 招标保证金不得超过招标项目估算价的百分之二",
  "applies_to": "bid | tender | both"
}]}
```

### 执行与进度

- 并发上限 `legal_mining_concurrency`（默认 3），受全局 `llm_max_concurrent` 二次收口。
- 单块超时 `legal_mining_timeout`（默认 180s）。
- **整过程是异步的**：`POST /generate` 立即返回 `status=pending`，
  后台 `asyncio.Task` 推进 `pending → mining → ready|failed`，前端轮询 `GET /{id}`。
  （与本项目审核任务模型一致，不用 SSE，降低前端改动。）
- 进度：切分占 0~5%，分块抽取占 5~85%，合并去重占 85~100%。
- **单块失败不致命**：记录 `failed_chunks` 并写入告警，该部分条款不纳入，其余照常产出。

## 5. 模块三：归一化 / 去重 / 打分截断

| 步骤 | 做法 |
|---|---|
| **归一化** `coerce_rule` | 类别/严重级别落白名单（非法 → `legal` / `major`）；名称 ≤60 字、说明 ≤500 字、要点 ≤6 条各 ≤200 字；**无 checkpoints 直接丢弃**（不可核查）；`need_legal_basis=False`（依据已内嵌，省一轮 50~80s 的 KB 查询） |
| **精确去重** | key = 条款号 + 规则名去标点归一化；保留要点更多的那条，合并依据条款 |
| **模糊去重** | `difflib` 序列比（不引入 embedding 依赖）。**阈值分档**：同条款号 0.70（容忍「2%」与「百分之二」的写法差异）；跨条款 0.86（避免把「投标保证金上限」与「履约保证金上限」误合并） |
| **打分截断** | `(严重级别权重, 含量化阈值, 要点数)` 降序，取前 `legal_max_rules`（默认 30）条，超出部分写入告警 |
| **id 稳定化** | 重排为 `lr-{规则集短码}-{序号}`，**不受并发完成顺序影响** —— 同输入必得同 id，保证可复现与跨任务比对 |

## 6. 模块四：临时规则集的管理

### 存储

`backend/data/legal_rulesets.json`（独立于 `rules_store.json`），随数据卷持久化。

```jsonc
{
  "id": "lrs-xxxxxxxxxxxx",
  "name": "招标投标法-临时规则",
  "status": "pending | mining | ready | failed",
  "progress": 100.0, "progress_message": "已生成 24 条规则",
  "owner_id": "u-xxx", "is_shared": false, "version": 1,
  "source_files": [{"file_id", "filename", "md5", "char_count"}],
  "sources_fingerprint": "md5(来源文件+参数)",     // 复用判定 & 可复现
  "params": {"mode", "max_rules", "chunk_chars", "llm_model"},
  "rules": [ /* 引擎可消费的规则 dict */ ],
  "warnings": ["《XX》超过处理上限 600000 字，已截断", "..."],
  "stats": {"source_chars", "chunks", "chunks_done", "raw_rules",
            "dedup_removed", "kept", "truncated", "failed_chunks", "split_mode"}
}
```

### 权限模型（与既有规则集完全一致）

管理员（`user_id=None`）可见/操作全部；普通用户仅「自己拥有的 + 系统共享的」。
⚠️ 路由层必须用 `deps.scope_user_id(caller)`（admin → `None`）做可见性过滤，
用 `_assert_owner` 做越权校验 —— 两者职责不同，混用会导致管理员改不了他人规则集。

### API（`backend/routers/legalrules.py`）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/legal-rules/preview` | **不调模型**，只算切分统计（块数/字符数/预计调用次数），供前端提示成本与可行性 |
| POST | `/api/legal-rules/generate` | 创建并启动生成任务，立即返回 |
| GET | `/api/legal-rules` | 列表 |
| GET | `/api/legal-rules/{id}` | 详情（含规则/进度/统计/告警），**生成中轮询此接口** |
| PATCH | `/api/legal-rules/{id}` | 改名/改说明/整体替换规则/改共享；替换规则时 `version` 递增 |
| DELETE | `/api/legal-rules/{id}` | 删除（不影响历史任务，任务已存元数据快照） |
| POST | `/api/legal-rules/{id}/promote` | **转正**：固化为正式自定义规则集，依据条款并入 `description` |

**复用缓存**：同源文件 + 同参数（`sources_fingerprint`）已生成过 `ready` 记录时直接复用，
避免重复烧 token（可用 `reuse=false` 强制重跑）。

### 配置项（已加入 `config.DEFAULTS` 与 `ConfigUpdate` 白名单）

| 配置 | 默认 | 说明 |
|---|---|---|
| `legal_chunk_chars` | 12000 | 单块字符预算 |
| `legal_max_rules` | 30 | 规则数上限 |
| `legal_mining_concurrency` | 3 | 分块抽取并发 |
| `legal_max_source_chars` | 600000 | 源文本处理上限（超出截断+告警） |
| `legal_mining_timeout` | 180 | 单块抽取读超时（秒） |

> ⚠️ 本项目配置分层：`BCR_*` env > SQLite > `runtime_config.json` > DEFAULTS。
> **只改 DEFAULTS 不生效**，须 `PATCH /api/settings` 写库；且新配置项必须显式加入
> `ConfigUpdate` 白名单模型，否则会被静默丢弃。

## 7. 模块五：与审核流程的衔接

### 两种模式（`ReviewRequest` 新增两个字段）

| 字段 | 说明 |
|---|---|
| `legal_ruleset_ids: list[str]` | 本次使用的法规临时规则集 |
| `legal_rules_only: bool \| None` | `True`=只跑法规规则；`False`=强制叠加；`None`（默认）=**自动判定** |

**自动判定逻辑**：未显式选择任何既有来源（无 `rule_group_ids`、无真实 `ruleset_id`、无 `rule_ids`）
→ 视为「只想用法规规则」，走**纯法规模式**；否则**叠加模式**。
（前端总会传合成的 `ruleset_id="mode-bid"` 与 `mode`，这两者不代表用户主动选了既有规则，故不计入判定。）

- **纯法规模式**：`_resolve_rules` 直接返回法规规则，不解析内置规则。
- **叠加模式**：既有规则在前、法规规则在后，按 id 去重合并。
- 规则集**不存在 / 无权限 / 尚未生成完成**（`status != ready`）→ 明确 400，
  **不静默降级**为「没有规则」，避免用户以为审核跑过了。

### 任务持久化与溯源

任务记录新增两个字段（临时规则集可被用户随时改删，不存快照则结论无法解释）：

- `legal_ruleset_ids: list[str]`
- `legal_rule_meta: [{id, name, version, rule_count, source_files, sources_fingerprint, llm_model, generated_at}]`

同时把「本次规则来自哪份法规」追加进 `extra_instruction`：

> 【法规临时规则】本次审核的部分规则由用户上传的法规文件自动生成：《招标投标法》(v1，24 条，来源：xx.pdf)。……

既提升判定准确性（模型知道依据哪部法规），也让报告可溯源。

## 8. 与既有规则组模式的差异

| 维度 | 既有规则组/规则集 | 法规临时规则集 |
|---|---|---|
| 规则来源 | 人工沉淀（内置常量 / 用户自定义 / CSV 导入） | 模型从法规文件自动抽取 |
| 稳定性 | 稳定，可长期复用 | 随模型/文件/参数波动，**需人工预览确认后才送审** |
| 存储 | `rules_store.json` / `rule_groups.json` | `legal_rulesets.json`（独立） |
| 生命周期 | 长期，显式删除才消失 | 默认临时；可「转正」为正式规则集 |
| 依据可溯源 | 靠 `need_legal_basis` 现查 KB（50~80s/次） | 依据条款已内嵌规则，`need_legal_basis=False`，**不查 KB** |
| 确定性条件 | 支持 `structured`（关键词/正则/金额阈值/两金额差值） | **不自动生成** —— 结构化字段需精确参数，模型易造错；如需应由人工在编辑页配置 |
| 一致性核查 | 可含 `consistency` 类规则，触发独立核查阶段 | 强制规避（见下），不触发 |
| 数量级 | 25~59 条内置规则 | 默认上限 30 条（可调） |
| 前置耗时 | 0 | 数十秒~数分钟（分块抽取） |
| 失败模式 | 规则缺失 → 报 400 | 分块可部分失败 → 产出告警 + 剩余规则照常可用 |

### ⚠️ 关键坑：一致性规则的误判

`rules_store.is_consistency_rule` 的判定是：
`category == "consistency"` **或** `id.startswith("cons-")` **或** （name 含「一致」**且** category ∈ `("", "qualification")`）。

一旦误命中，会额外触发一整段一致性核查（`consistency_timeout=600`），对法规派生规则毫无意义。
防护措施（`coerce_rule` 内）：

- id 用 `lr-` 前缀，绝不以 `cons-` 开头；
- Prompt 明确禁用 `consistency` 类别，归一化再兜底一次；
- 若模型给了 `qualification` 且名称含「一致」→ 强制改判 `legal`。

自检已断言 `is_consistency_rule(规则)` 全部为 `False`。

## 9. 边界情况与应对

| # | 边界情况 | 处理 | 状态 |
|---|---|---|---|
| 1 | 法规超长（百万字） | 超 `legal_max_source_chars` 截断 + 告警；分块并发控成本 | ✅ |
| 2 | 扫描版 PDF | 复用 OCR 通路，但 `MAX_OCR_PAGES=30`，超出页不识别 → 文本缺失告警 | ⚠️ 已知限制 |
| 3 | 无「第X条」结构（通知/意见） | 降级为章/段切分 + 告警提示条款边界不精确 | ✅ |
| 4 | 文件解析失败 / 空文本 | `create_ruleset` 直接 400 报具体文件名 | ✅ |
| 5 | 抽取不到任何可核查规则 | `status=failed` + 明确错误「未能抽取到任何可核查的规则」 | ✅ |
| 6 | 模型编造条款（幻觉） | Prompt 强约束 + `legal_basis` 随规则落盘供人工核对；**仍需人工预览把关** | ⚠️ 流程约束 |
| 7 | 规则过多（>30） | 按「严重级别 + 可量化程度」打分截断 + 告警 | ✅ |
| 8 | 跨块重复规则 | 精确（条款号+名称）+ 模糊（分档阈值）两级去重 | ✅ |
| 9 | 法规已废止 / 与新法冲突 | **系统无法自动判别**；建议前端展示 `source_files` 与生成时间，由用户负责 | ⚠️ 需人工 |
| 10 | 多份法规规则冲突 | 不做自动仲裁，全部保留并在 `legal_rule_meta` 记录来源，冲突由审核结论暴露 | ⚠️ 设计取舍 |
| 11 | 规则集生成中就被送审 | 400「尚未生成完成」，不静默降级 | ✅ |
| 12 | 生成中途服务重启 | 启动时 `_recover_interrupted()` 把非终态（pending/mining）翻为 `failed`，避免前端永久轮询 | ✅ |
| 13 | 临时规则集被删除 | 历史任务已存 `legal_rule_meta` 与规则快照，报告仍可解释 | ✅ |
| 14 | 法规文件被误当审核目标 | `role=legal` 在 `_resolve_docs` 拦截 400 | ✅ |
| 15 | 宣示性/倡导性条款 | 无具体核查要点的规则被 `coerce_rule` 丢弃 | ✅ |
| 16 | 确定性重跑的指纹 | 引擎 `rule_set_version` 尚未纳入临时规则集版本 | ⚠️ 待补：`version_manifest` 加入 `sources_fingerprint` |
| 17 | 权限越权 | 可见性走 `scope_user_id`，写操作走 `_assert_owner` | ✅ |
| 18 | 重复生成烧 token | `sources_fingerprint` 复用已 `ready` 规则集 | ✅ |
