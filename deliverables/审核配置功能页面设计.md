## 3. 联网搜索配置

**两层配置**（系统层开关密钥 + 任务层开关），端到端满足"为审核任务开启/关闭联网搜索"。

### 3.1 系统层（`SettingsDrawer` → 「联网搜索」分区）
- `web_search_enabled` Switch、`web_search_api` Select、`web_search_api_key` Input.Password（带测试）、最大结果/超时。
- 未填密钥时，任务层开关禁用。

### 3.2 任务层（工作台「审核选项」卡片）
- `启用联网搜索` Switch（disabled 直到 `web_search_api_key` 已配置）。
- 未配置时卡片内 `Alert`：`请在「服务配置」中配置联网搜索API密钥`。
- 提交任务：`web_search_enabled` → 后端 `review_engine` 调 `web_search_client`。

## 4. 知识库检索配置

**两层配置**（系统层服务+默认库 + 任务层启用+关联库），满足"配置其关联的检索知识库"。

### 4.1 系统层（`SettingsDrawer` → 「知识库」分区）
- `kb_base_url`（测试加载库列表）、`kb_id` Select（法规知识库）、`kb_api_key`、启用、最大检索次数、超时。

### 4.2 任务层（工作台「审核选项」卡片）
- `启用法规知识库检索` Switch（disabled 直到 `kb_id` 已选）。
- `关联检索知识库（本任务）` Select：列出系统层测试得到的库；**留空则用系统默认 `kb_id`**；未选时 `Alert` 引导。
- 提交任务：`kb_enabled` + `kb_id`（任务覆盖→系统默认）→ 后端 `kb_client.ask`。

## 5. 配置如何驱动一次审核（端到端）

```
系统配置(持久化 SQLite, 可 BCR_* 覆盖)
        │
        ├─ OCR 地址/密钥      ─┐
        ├─ 大模型 地址/密钥    ├─→ 提交审核任务时，后端按 config 注入
        ├─ 知识库 地址/库/密钥 ─┤   （OCR 解析 → 大模型审核 → 知识库检索 → 联网搜索）
        └─ 联网搜索 地址/密钥  ─┘
        │
任务配置(Drawer/卡片选择)
        ├─ 规则集/规则(rule_ids)
        ├─ 启用知识库(kb_enabled) + 关联库(kb_id?)
        └─ 启用联网搜索(web_search_enabled)
        │
        ▼
   POST /api/review/tasks  → 后台异步执行 → 进度/结论回传
```

- 优先级：`BCR_*` 环境变量 > 持久化 `config`（SQLite）> 任务级覆盖（仅 `kb_id` 允许任务级覆盖系统默认）。
- 密钥仅在后端落库，前端脱敏；前端负责"可配置 + 持久化 + 按配置调用"的入口与反馈。

## 7. 通用化改造（v2）：从"投标专属"升级为"通用文件审核"

> 需求：通用文件审核界面，支持用户配置**多种文件类型**匹配特定审核规则；界面含**文件类型配置 / 审核规则配置 / 审核规则组管理**；规则组支持**多选**；提供开关"自动根据文件分类匹配规则组"，但**系统不得自动对上传文件分类**（类型须由用户手动指定）。

### 7.1 信息架构（统一导航，单一入口）

```
顶栏（仅产品名 + 状态 + ⚙系统配置齿轮）
  └─ 导航条（唯一页面入口，集中管理，消除与顶栏重复）
       工作台 | 文件类型配置 | 审核规则组 | 审核规则 | 审核历史 | 反馈与训练数据
```
**布局修复**：原 v1 概念稿顶栏右上角有「规则管理 / 服务配置」、导航条又有「规则配置 / 系统配置」，两个"配置"入口重复显示。v2 改为——**所有页面入口仅由导航条承载**；顶栏只保留一个 `⚙ 系统配置` 齿轮（抽屉唯一触发点），不再有"规则管理""服务配置"等重复按钮。

### 7.2 新增/改造的页面

| 页面 | 类型 | 关键能力 |
|---|---|---|
| 文件类型配置 | 整页（`rm-page`） | 定义文件类型（招标/投标/合同/资质/通用），可设允许后缀，并**关联审核规则组（多选）** |
| 审核规则组 | 整页（`rm-page`） | 规则组的命名组合管理；右侧勾选本组包含的**具体规则**（规则来自「审核规则」页） |
| 审核规则 | 整页（`rm-page`） | 规则清单 CRUD（即原"规则配置"），规则可被归入多个规则组 |
| 工作台 | 双栏 | 上传文件（每文件**手动指定类型**）+ 审核规则组**多选** + 自动匹配开关 + 审核选项 |

### 7.3 工作台交互：规则组多选 + 自动匹配（核心）

1. **手动指定类型**：待审文件表格新增"文件类型"列，用户为每个文件下拉指定类型；界面明确提示"系统不会自动识别文件类型"。
2. **规则组多选**：工作台「审核规则组」卡片用 `grp-chip`（胶囊）多选；每个芯片可独立勾选，支持任意组合。
3. **自动匹配开关**（`autoMatch`）：
   - 开启 → 依据用户**手动指定的文件类型**，自动勾选其关联的规则组（取各文件类型关联组的并集），并可在此基础上手动增删。
   - 关闭 → 完全由用户手动多选规则组。
   - **系统绝不自动分类文件**：自动匹配的输入是"用户指定的类型"，而非文件内容识别；前端 `FT_GROUPS` 为类型→规则组映射示例。
4. 提交：`POST /api/review/tasks` 携带 `rule_group_ids`（多选）+ 各文件 `file_type` + 任务级联网/知识库开关。

### 7.4 数据模型（建议后端扩展）

```python
FileType:   { id, name, desc, extensions: list[str], rule_group_ids: list[str] }   # 类型→规则组映射
RuleGroup:  { id, name, rule_ids: list[str], desc }                                 # 规则组→规则映射（多选套用）
Rule:       { id, name, category, severity, points, needs_kb }                      # 原子规则（沿用现有）
ReviewTask: { file_ids, file_types: dict[file_id->type], rule_group_ids: list[str],
              auto_match: bool, kb_enabled, kb_id?, web_search_enabled, extra }
```

### 7.5 原型

`prototype/file-review.html`（v2）已按上述重构：通用标题、单入口导航、文件类型配置页、审核规则组页、工作台规则组多选与自动匹配开关；JS 通过语法校验。点击导航即可体验全部流程。

## 8. 真实前后端集成落地（v2 实现，非仅原型）

> 上一节为设计规范与原型；本节为**已落地的真实代码**，与现有 `frontend/src`（React+Antd5+TS）和 `backend/`（FastAPI+JSON 持久化）对接。验证：`tsc --noEmit` 通过、`vite build` 通过、后端 `py_compile` 全部通过、FastAPI 应用导入成功（36 条路由，含新增 8 条）。

### 8.1 后端新增 / 改动

| 模块 | 文件 | 说明 |
|---|---|---|
| 文件类型存储 | `backend/services/file_types.py` | JSON 存储 `file_types.json`，预置 5 类：`ft-tender` 招标 / `ft-bid` 投标 / `ft-contract` 合同 / `ft-qualification` 资质 / `ft-general` 通用；每项含 `extensions`、`rule_group_ids` |
| 规则组存储 | `backend/services/rule_groups.py` | JSON 存储 `rule_groups.json`，预置 5 组：`rg-completeness` 完整性 / `rg-consistency` 一致性 / `rg-format` 格式 / `rg-compliance` 合规 / `rg-signature` 签章；`expand_rule_groups(ids)` 按 id 跨投标/招标/通用三套规则 + 自定义规则集聚合去重 |
| 文件类型路由 | `backend/routers/file_types.py` | `GET /api/file-types`、`GET /{id}`、`POST /api/file-types`、`DELETE /{id}` |
| 规则组路由 | `backend/routers/rulegroups.py` | `GET /api/rule-groups`、`GET /{id}`、`POST /api/rule-groups`、`DELETE /{id}` |
| 主应用挂载 | `backend/main.py` | 注册上述两个 router |
| Schema 扩展 | `backend/models/schemas.py` | `UploadedFile` 增 `file_type`、`validation`；新增 `FileValidation{ok,level,messages}`、`FileType`、`RuleGroup`；`ReviewRequest` 增 `file_types`、`rule_group_ids`、`auto_match` |
| 文件存储 | `backend/services/file_store.py` | `save_and_parse` 增加类型后缀约束与 `validation` 写入；新增 `set_file_type`（`PATCH /files/{id}/type`）；`_role_for_file_type` 将类型映射到 role（招标→tender / 投标→bid / 其他→attachment） |
| 规则解析 | `backend/routers/review.py` | `_resolve_rules` 优先级：`rule_group_ids`（+ auto_match 依文件 `file_type` 关联组并集）> 真实规则集 > mode；为空则 400；`_resolve_docs` 对空文本文件返回结构化 `{errors:[...]}` |

**四层校验能力（后端增强）**：① 格式（`doc_parser.SUPPORTED` 扩展名校验）；② 大小（`MAX_FILE_SIZE` 100MB）；③ 类型后缀约束（文件类型声明的 `extensions`）；④ 内容（解析失败 / 空文本判定为不可用，附 `validation` 反馈）。

**规则解析优先级**：`rule_group_ids` 显式指定 > `auto_match` 依用户手动指定文件类型并集其关联规则组 > 真实规则集（ruleset_id）> 审核模式（mode）。`auto_match` 的输入严格是"用户指定的文件类型"，系统**绝不自动识别文件内容**。

### 8.3 端到端覆盖

```
上传(指定类型) → save_and_parse(格式/大小/类型后缀/内容校验 → validation) 
   → PATCH /files/{id}/type(可改类型，role 联动)
```
