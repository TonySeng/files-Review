# 规则优化：中标价与暂估价「异常接近」核查

> 适用规则：原「审核评标报告中最终中标候选人的投标价与项目的暂估价完全相同或者差值小于暂估价的10%则触发该规则，判断为不合规」
> 两轮迭代：第一轮改规则文案（已交付）；第二轮根据实测反馈定位到**真正的根因**并改代码（已实现）。

---

## 零、第二轮实测暴露的真根因：不是「推理混乱」，是「提交顺序」错了

第一轮改完文案后重测，模型的表现是：

- 数值**算了 8 遍，每一遍都对**：R = 20.7 ÷ 172.7 = 11.98% ≥ 10%
- 结论词**说了 8 遍 pass**
- 但结构化字段 `status` **仍然是 fail**

→ 这不是推理问题，是**自回归提交顺序**问题。

提示词里 JSON 示例的字段顺序是：
```
"rule_id" → "status" → "title" → "detail" → ...
```
`status` 排在第 2 位，模型必须在写下任何理由之前就吐出 `status`。它凭规则名（含「异常/风险/相似度」等字样的先验）先填了 `fail`，然后在 `detail` 里认真算完发现应该是 pass —— 但 `status` 的 token 早就发出去，改不回来了。

系统侧的 `_finding_text_contradicts_fail` 检出这个矛盾 → 降级 `unknown` → 用户看到「待人工复核」。

**所以：文案改得再好，只要 `status` 仍在 `detail` 之前生成，就会周期性复现。**

## 一、已实施的修复

### 修复 1：提示词字段顺序（治本，对所有规则生效）

`backend/services/prompt_store.py` → `_BUILTIN_REVIEW_RULE`

```
"rule_id" → "detail" → "title" → "status" → "evidence" → ...
```
并新增【填写顺序(强制)】四条指令，明确：
1. 先写 `detail`（摘录原文 → 算术校验 → 末尾写出结论词）；
2. 再写 `title`/`status`，`status` 必须复制 `detail` 末尾的结论词；
3. 严禁先定 `status` 再倒推理由（否则矛盾会被检出并降级）；
4. **数值类规则：只有数值满足触发条件才填 fail；数值落在合规区间时，即使规则名含「异常/风险/敏感度」也必须填 pass。**

> ⚠️ 上线注意：提示词一旦被持久化过，改内置模板**不会自动生效**。部署到 131 后需执行一次
> 「提示词管理 → 规则核查提示词 → 重置为内置默认」（接口 `POST /api/prompts/review_rule/reset`）。
> 若该模板此前人工改过，重置会丢失自定义内容，需手工把新增的两段合并进去。

### 修复 2：确定性引擎支持相对阈值 `max_ratio`（本规则的根治方案）

原先 `amount_pair_diff` 只有绝对阈值 `max_abs_diff`（元），「差值小于暂估价的 10%」这种**随基准浮动**的阈值配不出来，只能回落 LLM。

| 文件 | 改动 |
|---|---|
| `backend/services/rules_store.py` | 新增 `_opt_float`（区分「未配置」与「阈值就是 0」）；`_normalize_structured` 的 `amount_pair_diff` 支持 `max_ratio`（0.1 = 10%）+ `ratio_base`（`"a"`\|`"b"` 指定分母），与 `max_abs_diff` 二选一，皆缺则丢弃 |
| `backend/services/review_engine.py` | 新增同名 `_opt_float`；判定段优先用相对阈值 `threshold = 基准值 × ratio`；结论文案输出差异率与阈值百分比；比较符按 `fail_when` 渲染（≤/< /≥/>） |
| `backend/services/prompt_store.py` | 法规抽取（`_BUILTIN_MINING_SYSTEM`）的 `structured_hint` 说明同步支持 `max_ratio`/`ratio_base` |
| `frontend/src/types/index.ts` | `StructuredCondition.amount_pair_diff` 增加 `max_ratio` / `ratio_base`，`max_abs_diff` 改为可选 |

本规则应配的 structured：

```json
{
  "amount_pair_diff": [
    {
      "a_field": ["暂估价"],
      "b_field": ["中标价", "投标价", "预中标价"],
      "max_ratio": 0.1,
      "ratio_base": "a",
      "fail_when": "lt"
    }
  ]
}
```

配好后该规则由代码锁定结论（`deterministic=True, confidence=1.0`），**不再调用 LLM、不再矛盾、不会降级**。`structured` 已计入 `versioning.rule_content_hash`，加配置后历史结论缓存自动失效。

> 应用方式：前端规则编辑弹窗没有 `amount_pair_diff` 的录入项，但它会**原样保留**已有的 structured 字段（只覆盖 `consistency_elements`），
> 所以通过规则集保存接口（把 `structured` 一并带上）或直改 `app.db` 均可。需要的话我可以写一个按规则名批量注入的迁移脚本。

### 修复 3：`_extract_amount_near` 支持「单位前置」（否则修复 2 会失效）

实测原文是 **「暂估价(万元) 172.7」——单位写在数字前面**。原抽取器只认后置单位，会把它读成 **172.7 元**，而中标价「152.000000万元」读成 1,520,000 元，两者差百万倍，确定性判定必然失真（且漏判真正的违规）。

新增 `_leading_unit()`：后置单位缺失时回看数字前的短前缀，若是单位声明则套用。**前缀限长 4 字**——过长说明中间夹了别的词（如「(万元)：本次招标控制价 5000」），单位与数字已非直接修饰关系，宁可不套用，避免错乘。

## 三、第一轮交付的规则文案（仍然建议一并采用）

### 规则名称
```
中标价与暂估价异常接近（疑似泄露暂估价）
```

### 规则说明（条件）
```
【业务意图】暂估价属于招标控制性价格信息。正常竞争下中标价应明显低于暂估价；
若中标价与暂估价"完全一致"或"差异过小（＜暂估价的 10%）"，说明投标人可能提前
获知暂估价、报价缺乏竞争性，属异常接近，判定为不合规。

【判定口径】
- A = 项目暂估价：仅采信文件中明确标注为「暂估价」的金额。不得用「概算价」
  「预算价」「控制价」「最高限价」等替代；文件中若无「暂估价」字样或无法定位
  其数值，本规则无法判定。
- B = 最终中标候选人（第一中标候选人 / 预中标人）的投标价（中标价）。
- 两值统一换算为「元」后比较：R = |A − B| ÷ A（以暂估价 A 为分母，取绝对值）。
- 本规则只做数值判定；文件中「暂估价/概算价」术语混用属术语规范问题，
  由其他规则核查，本规则不因术语混用而改判。

【结论映射（唯一，不得并存）】
- R = 0（两值完全一致） 或 R ＜ 10%  → fail（不合规：中标价与暂估价异常接近）
- R ≥ 10%                            → pass（合规：差异充分）
- A 或 B 任一缺失 / 无法定位 / 多值冲突 → unknown（禁止猜测，禁止用其他价格顶替）
```

### 审核要点（每行一条）
```
1. 从评标报告/中标候选人公示中定位「项目暂估价」金额 A 与「最终中标候选人（第一中标候选人/预中标人）投标价（中标价）」B，摘录原文并在 detail 中写明 A=…元、B=…元。二者任一缺失或无法定位 → 直接判 unknown 并在 detail 说明缺哪一项；严禁用概算价、预算价、控制价、最高限价等替代暂估价。
2. 计算差异率 R = |A − B| ÷ A（以暂估价 A 为分母，取绝对值），在 detail 中列出完整算式与百分比结果（保留两位小数），并与 10% 阈值比较。
3. 按唯一映射出结论：R = 0 或 R ＜ 10% → fail；R ≥ 10% → pass。R ≥ 10% 时一律判 pass，不得因报告中出现其他价格差（如初始报价与中标价的差额 6.835 万元）、或「暂估价/概算价」术语不一致，而改判为 fail 或 unknown。
```
